## 1. Executive Summary

HIVER_SUPPORT_AGENT is a hybrid intent-classification + retrieval-grounded
reply-generation + explicit-escalation system for one brand's Twitter
customer support, built end-to-end and reproducible in under 15 minutes in
fast/demo mode (`python scripts/run_all.py --fast`). The full evaluation
harness — two baselines, an LLM judge, human-agreement measurement, failure
analysis, and automated leakage checks — is implemented and runs without
requiring an LLM API key for the core pipeline. Real headline numbers on the
actual Kaggle dataset are `PENDING` acquisition of that dataset and human
annotation of the 200-example golden set; see Sections 10–13.

## 2. Problem Framing

Given real historical Twitter support conversations for one brand, decide
per incoming message: what does the customer want (intent), what's the best
grounded reply based on how this brand has actually resolved similar issues
before, and can this be safely auto-handled or does it need a human. The
system must prioritize **evidence over architecture**: every reported number
must be reproducible from files in this repository, and nothing is
fabricated.

## 3. What "Good" Means for This Brand

Good means: (1) intents are recognizable to someone who has read this
brand's actual support traffic, not generic textbook categories, (2) replies
never state a price, timeline, or policy that isn't backed by the
customer's own message or a real historical resolution, and (3) the system
escalates aggressively enough that `unsafe_auto_handling_rate` (gold=
ESCALATE, predicted=AUTO_HANDLE) stays low, even if that means automating
fewer tickets.

## 4. What We Chose NOT to Build

- No fine-tuned/custom LLM — an off-the-shelf embedding model +
  calibrated logistic regression + optional API-based LLM generation is
  simpler, faster to evaluate, and keeps the core pipeline runnable without
  any API key.
- No automatic entity substitution (e.g. auto-inserting the current order
  ID into a templated historical reply) in the LLM-free fallback — too easy
  to silently insert something wrong; see decision log #9.
- No BLEU/ROUGE as a headline metric — poor proxy for groundedness/safety;
  see decision log #10.
- No multi-brand system — the assignment scope is one brand, done well,
  over many brands, done shallowly.

## 14. What Is Misleading About My Headline Number?

Whatever the headline metric turns out to be (recommended: golden-set
Macro-F1 for intent classification, or Safe Automation Rate = automation
rate conditioned on `unsafe_auto_handling_rate` staying near zero, for the
end-to-end system — see `docs/evaluation_protocol.md` Section 9), it is
misleading in at least these ways:

- **Small golden set (150–250 examples).** Confidence intervals on any rate
  computed from ~200 examples are wide; a macro-F1 of 0.75 vs 0.70 on 200
  examples is not necessarily a meaningfully different system.
- **Single brand.** Every number is specific to one brand's support style,
  vocabulary, and issue mix. Nothing here generalizes to a different brand
  without re-running brand selection, intent discovery, and re-annotation.
- **Temporal/data-distribution limitations.** The chronological split means
  test-period performance reflects whatever issues were trending in that
  window (e.g. a shipping outage) — it is not a stable estimate of
  steady-state performance.
- **Human labeling subjectivity.** Intent and escalation labels involve
  judgment calls (see `data/golden/annotation_guide.md` "Handling ambiguous
  cases"); a second annotator would not label identically on every example,
  and no formal inter-annotator agreement was computed for the golden set
  itself (only for the LLM-judge-vs-human check).
- **Evaluation set may not represent rare edge cases.** Stratified sampling
  covers length/time-period strata, not rare-but-important scenarios (e.g.
  a fraud report); rare failure modes can be entirely absent from a
  200-example set.
- **LLM judge bias.** LLM judges are known to favor longer, more
  confident-sounding replies and can be inconsistent across near-identical
  inputs; the human-agreement check bounds but does not eliminate this.
- **Historical replies may themselves contain inconsistent support
  behavior.** "Grounded in historical evidence" is not the same as
  "correct" — if past agents gave inconsistent or suboptimal answers, a
  well-grounded reply can faithfully reproduce a bad pattern.
- **Successful benchmark results do not guarantee production safety.** A
  low `unsafe_auto_handling_rate` on 200 offline examples says nothing about
  adversarial inputs, multi-turn conversations, or account-specific edge
  cases not represented in the dataset.
- **Automation rate can be misleading if aggressive escalation is used.** A
  system that escalates almost everything can post a near-zero unsafe rate
  while providing little actual automation value — automation rate and
  unsafe rate must always be read together, never automation rate alone.
- **Macro-F1 can hide costly errors in particular intents.** A model can
  have strong macro-F1 while performing poorly on one high-stakes intent
  (e.g. REFUND_REQUEST) that a support team cares about most; per-intent F1
  (`outputs/metrics/main_system_metrics.json` → `classification.per_intent`)
  must always be checked alongside the macro number.

## 15. What I'd Do With One More Week

1. Get the real Kaggle dataset loaded and re-run brand selection, intent
   discovery, and the full 200-example human annotation pass — everything
   in this repo is built to consume it immediately.
2. Run the human-agreement study properly (50 examples, real annotator,
   same rubric as the LLM judge) to actually validate the judge rather than
   leaving it `PENDING`.
3. Replace the keyword-based weak-labeler stand-in
   (`scripts/05_train.py::_weak_label_from_keywords`, currently used only so
   the synthetic demo can exercise training end-to-end) with the real
   human-reviewed cluster→intent mapping via `src/intents/label.py`.
4. Add inter-annotator agreement on the golden set itself (a second
   annotator labels a 30-example subset) to quantify labeling subjectivity,
   not just judge-vs-human agreement.
5. Expand the escalation policy's high-risk keyword list based on real
   false-negative escalations found in failure analysis, rather than the
   starter list in `configs/config.yaml`.
6. Try a smarter LLM-free fallback that safely substitutes only
   already-present entities (e.g. reusing the *customer's own* order number
   mentioned in their message, never inventing one) instead of returning the
   historical reply verbatim.
7. Add a lightweight regression test that re-runs the golden-set evaluation
   on every commit and fails CI if `unsafe_auto_handling_rate` regresses
   above a fixed budget.
